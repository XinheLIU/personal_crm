# 04 — 大模型 / 知识库 / 智能体 / Context Engineering

> Last updated: 2026/05/05

## TL;DR

阳光的大模型管理路线：**通用大模型业务定制化（小模型 / 微调）+ 评审委员会 + 阳光的市场化模式**（项目组定上马）。当前主用 **Qwen2.5**，未来 **Qwen3 微调训练 + R1 蒸馏**。**知识库**演进路径：**QA 问答库 → 文档（多类型 / 高准确率要求）→ RAG flow + 现在定制化**；王睿牵头两块（内容 + 技术方向）；模型 / 算力另两个部门管理。**智能体 18 个项目分 3 类**：① 需要数据反馈的（4 个）— 自主闭环 + RLHF 进化；② 仅使用大模型功能的（7 个）— 文本生成、无闭环；③ 可能是传统模型的（6 个）— 无大模型交互、无自主闭环。这个分类**暴露了当前规划中智能体概念的混淆**。**月牙观察**强调三件事：**首先要有架构师角色 + Context engineering 排序 + 强基模实践 + 人员采纳能力**。

## 智能体分类（3 类 18 项目）

> 来自原文对现有项目的分类 — 暴露了当前规划中智能体概念的混淆 + 缺乏统一的评估标准和演进路径。

### 类别 1：需要数据反馈的智能体（4 个）
- **特征**：自主闭环能力 + 需要高质量反馈数据持续进化
- **代表**：客户运营管理机器人 / 机构风险透视管理机器人

### 类别 2：仅使用大模型功能的机器人（7 个）
- **特征**：依赖大模型的文本生成、信息提炼或专业决策能力，**不具备持续进化的闭环机制**
- **代表**：投研分析助手 / 智能客服机器人

### 类别 3：可能是传统模型的机器人（6 个）
- **特征**：依赖传统算法模型实现辅助分析，**无大模型的复杂交互能力，也无智能体的自主闭环执行能力**
- **代表**：四级机构管理机器人 / 智能物控系统

### 这个分类的洞察
- 暴露**当前规划中智能体概念的混淆**
- 缺乏**统一的评估标准和演进路径**
- → 详见 [05 IT 转型](05-enterprise-it-transformation.md) 中的"价值衡量与迭代闭环缺失"
